## Layout and motion

Two adjacent columns share the drawer width, 48% for prose and 52% for artwork, separated by 32px. A 24px top inset separates the composition from the pillar headings. Three paragraphs cover imaging roots, DIGITX’s continuation and current challenge studies, with 24px between paragraphs. The desktop image stage scales from 420px to 560px to balance the expanded challenge-study paragraph; the columns’ vertical centres align, including the caption. Shared body typography is unchanged. The drawer has no top or bottom rule and no separate close row; the heading minus and Escape still close it. The side figures sit closer to the stage edges, and each card’s hit area matches its rendered portrait. Below 1200px the columns stack, using a 24px gap and 16px top inset. The stacked image stage remains 300–360px. The view is inspired by the publicly documented coverflow behaviour at https://pro.reactbits.dev/docs/components/prism-carousel, whose sweep and dispersion options are distinct from its movement. This implementation uses the site's existing Framer Motion dependency; it does not incorporate React Bits Pro source code or require a new paid package. No spectrum sweep, dispersion, scanner-name tabs or bottom controls. Each image and its permanent caption share the same horizontal MotionValue. Captions sit above the artwork so neighbouring image backgrounds cannot cover their text; their hit areas are only as wide as the words. Only the artwork scales and turns, so the label keeps the metadata type size and remains upright. A small vertical offset follows the scaled image’s lower edge. There is no shared visible caption to jump at midpoint handoffs. The hidden figure description identifies the centred view without a live region or repeated announcements. The stage reserves the same 36px caption space and clips outgoing pairs only at the transparent edge.

A single MotionValue advances continuously by one view every 6.5 seconds. Three stable image elements derive their horizontal position, depth, scale and opacity from that value. Views recycle only at the fully transparent outer edge. There is no React render per animation frame and no autoplay interval that snaps between slides.

Hovering anywhere within the image stage freezes the loop at its current position. Moving the pointer between figures does not select or move anything. Clicking a figure smoothly brings it to the centre. The loop resumes from the current position when the pointer leaves; mouse clicks never latch a pause. Selection is deliberately click-driven so a moving card cannot trigger further selections under a stationary pointer. Keyboard focus pauses, arrow keys choose the view, and Enter holds or releases the pause. On touch, tapping a figure focuses and holds it; tapping the same figure again releases it. Reduced motion is observed through a live matchMedia subscription. Offscreen, hidden tabs, loading and reduced-motion preferences stop the frame loop. Returning resumes from the held position with a fresh timestamp. Only three images are mounted, and no requestAnimationFrame loop remains active while paused. The accessible name and hidden description explain the pause/hold behaviour without announcing every moving image.

## Caption centring under browser zoom

A screenshot revealed an image/label offset that was absent at 100% zoom. Reproduced in WebKit with 75% document zoom and a 2× device scale: the image centre diverged by about 35 CSS pixels, while Chromium stayed aligned. The image used `left: calc(50% - var(--modality-card-width) / 2)` and the label used percentage translation; WebKit applied the width calculation inconsistently under zoom. Images and labels now share `left: 50%` and `translate: -50% 0`, alongside their existing shared horizontal MotionValue. Avoid restoring the calculated left offset.
